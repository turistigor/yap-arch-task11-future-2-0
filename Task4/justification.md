# Обоснование событийного подхода vs Camel/DWH

| Категория сравнения | ESB (Camel) + DWH | EDA (Kafka)|
|---|---|---|
| *Гибкость при изменениях* |
| Добавление внутренних участников | **Трудоёмкое**<br>маршруты заданы жестко | **Простое**<br>в коде новых участников |
| Добавление внешних интеграций | **Простое**<br>Много готовых коннекторов и других возможностей | **Трудоёмкое**<br>Нужно настраивать коннекторы |
| Изменение формата данных | **Трудоёмкое**<br>Затрагивает всех интересантов | **Проще**<br>За счет версионирования и обратной совместимости |
| Изменение логики обработки | **Трудоёмкое**<br>Логика в общем DWH | **Простое**<br>Локальные изменения в сервисах |
| *Производительность* |
| Горизонтальное масштабирование | **Менее эффективно**<br> Синхронизации между инстансами шины | **Эффективное**<br> за счет партиционирования |
| RPS | **Средняя**<br>~10 KRPS  | **Высокая**<br>~1 MRPS |
| Latency     | **Высокая, деградирует под нагрузкой**<br>~3ms, деградирует из-за Message-by-message | **Средняя, но устойчивая**<br>~10 ms, стабильна благодаря batching-у |
| *Отказоустойчивость* |
| Медленный consumer | **Отказ**<br> Переполнение очереди в RAM | **Не проблема**<br> Сохранение на диск |
| При падении шины | **Потеря данных**<br> stateless сервис | **Сохранение**<br> stateful сервис |
| При падении хранилища | **Отказ**<br> Так как хранилище общее | **Ограниченная работа**<br> Не работает только упавшая часть |

**Выводы**:

В текущей архитектуре велик риск превращения центральных компонентов в bottleneck-и (или общие точки отказа). EDA обладает большей гибкостью и отказоустойчивостью за счет меньшей связности компонентов. Кроме того её компоненты можно развивать независимо, применя  разные инструменты, процессы развертывания и способы масштабирования.
